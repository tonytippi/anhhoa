- (direction) SPEC is derived in express mode from final PassionEdu PRD/addendum and final Architecture Spine; upstream artifacts remain adopted companions.
- (decision) PassionEdu is a clean-break multi-school kindergarten operations platform; Anh Hoa is the first School tenant, not the product boundary.
- (capability) CAP-1: Platform Operators can provision, suspend and bootstrap independent Schools without implicit business-data access; success is atomic setup and next-request suspension enforcement.
- (capability) CAP-2: Admin, Staff and Parent access resolves in the authorized School context; success is no cross-school read/write/report access and next-request revoke without removing valid other-School access.
- (capability) CAP-3: Schools manage effective-dated settings, years, roster, Parent and Staff records; success is auditable historical enrollment/assignment without destructive overwrite.
- (capability) CAP-4: Finance configures receivables and CollectionRuns and creates authoritative draft obligations; success is one Invoice per Student per run with reconciled idempotent generation.
- (capability) CAP-5: Finance issues snapshot obligations and maintains append-only receipts, allocations, prepayments, reversals, refunds, debt and reports; success is reconcilable ledger totals and corrected mistakes without history mutation.
- (capability) CAP-6: Authorized Staff/Parents manage leave, attendance, services and handover under School policy; success is consistent conflicts, protected evidence lifecycle and Finance reference without auto-pricing.
- (capability) CAP-7: Parents use a multi-school read-only portal for authorized obligations and payment instruction; success is minimum authorized data and client-state clearing after revoke, expiry or logout.
- (constraint) School scopes all business records, policies, queries, audit and idempotent operations; server authorizes every request and never trusts browser school selection, UUID, header or filter.
- (constraint) API is authoritative for authorization, policy, VND integer calculations, state transitions, snapshots and reports; browser clients use REST only.
- (constraint) Issued obligations and payment instructions are snapshotted; finance postings are append-only, high-impact cookie mutations use origin validation, CSRF, idempotency and operation reconciliation.
- (constraint) Parent access derives only from active StudentParent links, uses minimum DTOs, forbids protected service-worker caching and applies server-side retention.
- (constraint) Release requires tenant isolation, revoke, ledger concurrency/idempotency and Parent cross-school verification; production uses the final Spine VPS recovery, performance and rate-limit envelope.
- (decision) Non-goals exclude compatibility/dual legacy model, bank sync or Parent payment confirmation, VAT, custom roles/organization hierarchy, JIT support, communications/media/medical/transport/HR/import-export, auto-pricing and Parent finance mutation.
- (assumption) VietQR, payment-field copy and bank deep links are deferred Parent enhancements; E7 MVP requires only read-only snapshot payment instruction.
- (question) Choose the registry, reverse-proxy implementation and offsite backup provider during deployment design while preserving the final Architecture Spine production envelope.
- (event) Self-validation coherence pass initially found CAP-6 success too vague and one non-binding architecture pointer; both were corrected.
- (event) Self-validation coherence pass PASS after CAP-6 observable outcomes and constraint cleanup.
- (event) Self-validation preservation pass PASS: SPEC plus adopted companions preserve load-bearing PRD, Architecture Spine and approved replan claims.
- (decision) Pilot release uses VPS source builds without container registry or backup; public/operational production recovery, monitoring, SLO, rate-limit and cloud decisions require a Spine update.
- (event) SPEC re-derived after pilot deployment decision; adopted Architecture Spine remains the deployment authority.
- (change) CAP-7 now includes authorized daily attendance read model with explicit statuses, NOT_RECORDED semantics and no Staff/evidence/internal-reason disclosure.
- (correction) Synchronized CAP-4/CAP-5 exact settlement and negotiated Student promotional coverage contract.
